## 2. 关联解析 (形态由第 1 节决定)

- [x] 2.1 恢复 poke 生成一次性 nonce 并与目标 pane 一起记账; 话术要求 codex 注册时回带; `register_agent` 接受可选 nonce, 命中即确定选中该 pane 的行; 未命中/未带一律回落现状, **决不猜**
- [x] 2.2 关联结果必须与 daemon 侧证据交叉校验: 解析出的 uuid 必须确实出现在某个可见 pane 的载体 argv 上 (C4); 不符即 fail-closed, **不得退回计数** (design R3)
- [x] 2.3 **caller 自报的 `xats.agent_id` 一律不采用** (E1 已否): 除信任分析那条理由外, 实测显示诚实 caller 也可能靠编造的理由答出正确值, 而 daemon 分不出推导与编造
- [x] 2.4 关联路径的成功与失败**都**要日志, 不能只在失败时出现 (design R4: 否则 `candidate_count` 变罕见反而掩盖关联失效)

## 3. 扫描改用关联选行

- [x] 3.1 `autoBindCodexPane`: 关联可得时按它选行, 候选唯一性降级为兜底 (关联不可得时的现状行为)
- [x] 3.2 关联选中的行仍要走完整的既有证据链 (前台载体证明 + identity_key 归属仲裁 + 快照一致 + 事务内重仲裁), 关联**只负责选行**, 不豁免任何一道
- [x] 3.3 关联选中多行 (不应发生) → 定向按 pane_id 过滤, 结构上最多一行; 多于一行仍走既有 `candidate_count` fail-closed
- [x] 3.4 单元测试: 两条待消费行 + 关联指向其中一条 → 只消费那条, 另一条原样保留; 关联不可得 → 回落计数并与现状逐字一致; 关联与载体证据不符 → 不绑不消费

## 4. 写入侧仲裁 (依赖第 2 节, 解决 S9)

- [ ] 4.1 `pre_register_codex_pane` 写入加归属判定: 覆盖一行**未过期**的行时, 写入方必须能被证明是该 pane 的 launcher.  **注意: M9 帮不上这里** —— nonce 是发恢复 poke 时铸的, 而预注册写入发生在 codex 启动**之前**, 那一刻没有任何 nonce.  所以候选判据回到 "**带的 key 等于行上那把**" + "**只在该行自己的载体还活着时才保护**" (进程存在即可, 不看前台)
- [ ] 4.2 S9 三个方向 (不带 key / 带受害者的 key / 带另一把 key) 全部转绿, 且**反向顺序仍绿** (损害自愈边界不得被破坏)
- [ ] 4.3 明确保留冷启动语义: tmux server 清空后 pane id 从 `%0` 重发, 旧行对应的载体**确证不存在**时不得挡住新 launcher (否则事故之后成批降级)

## 5. 回归与实验室

- [x] 5.1 全量单测与类型检查; 全量场景重扫 9/9 表逐格对比, 只有目标格变化
- [x] 5.2 真身复核 (2026-07-31, 私有实验室): N3 红证 (`candidate_count candidates=2`) → N1 绿 (`targeted … rows=1 pending_total=2`, 两条各被各自 caller 消费) → N2 绿 (无关行原样保留).  红证取自**同一份夹具去掉 nonce 那一臂** —— 新代码里 N1/N2 的红已产不出来
