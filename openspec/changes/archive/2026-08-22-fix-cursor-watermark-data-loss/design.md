## Context

`last_processed_event_id` 是 xats 判断"消息是否被读过"的唯一真相。  `get_inbox` 在返回行的同一事务里推进它, `add-message-read-ack` 用 `cursor >= event_id` 作为送达收据, `poke-retry` 用它抑制幽灵通知。

而 `applySchema` 里有第二个写入方: `migrateAgentsCursorWatermark`。  它不是 daemon 运行期的逻辑, 是一条每次启动都跑的迁移, 于是"游标只由收件人自己推进"这个前提在启动瞬间不成立。

根因是哨兵值 `0` 承载了两个互斥语义:

| 游标为 0 的来源 | 该不该推进 |
|---|---|
| 游标特性落地之前注册的行: 该列自建表起就带 `DEFAULT 0`, 但当时的注册 INSERT 不列它, 于是取到默认值 | 该 —— 否则重放整个历史信箱 |
| `register_agent` 在 `events` 空表上初始化 `COALESCE(MAX(event_id), 0)` | **不该** —— 这个 0 是准确的 |

两者在数据上完全同形, 无法区分。

第二类**不是只在全新库的第一天出现**。  `runCleanup` 对 `events` 执行 30 天硬 TTL (`DELETE FROM events WHERE created_at < ?`), 所以任何安静满 30 天的部署, events 表会重新变空; 此后新注册的 agent 又会拿到合法的游标 0, 又落进旧迁移的射程。  旧代码的伤害因此不是"每个库一次", 而是"每次库空闲满 30 天后再来新 agent 就复发一次"。

## Goals / Non-Goals

**Goals:**

- 让 `applySchema` 不再改写任何 agent 的游标。
- 恢复"游标只有 `get_inbox` 与注册初始化两个写入方"这一不变量, 使 `add-message-read-ack` 的收据论证重新成立。
- 不新增列、不新增迁移表、不引入版本标志。

**Non-Goals:**

- 不改 `register_agent` 的游标初始化。  `COALESCE(MAX(event_id), 0)` 是正确的: 新 agent 不该看到注册前的历史邮件, 而空 events 表上的 0 恰好也是正确答案。
- 不为陈旧库补做一次性推进 (理由见 D2)。
- 不追查生产库里已经被这条 bug 吃掉的消息。  游标已经推进, 原消息行仍在 `messages` 表中直到 30 天保留期到期, 但"哪些消息被误标已读"无法从现有数据反推。

## Decisions

### D1: 删除迁移, 而不是修好哨兵

**替代方案 A —— 让游标列可空**, 用 `NULL` 表示"从未初始化", `0` 表示"合法为零"。  语义上最干净。  **否决理由**: SQLite 不支持 `ALTER COLUMN`, 去掉 `NOT NULL` 需要 12 步建表重写整张 `agents` 表 —— 那是本仓库风险最高的一张表 (身份、pane 归属、identity key 都在上面), 为一条早已完成使命的迁移做全表重建不成比例。  且所有读取方都要开始处理 `NULL`。

**替代方案 B —— 加一个 `cursor_initialized` 标志列**, 迁移只看该列。  **否决理由**: 加列时必须给存量行回填, 而回填值面对的正是同一个不可区分问题 —— 加一列不会凭空产生你没有的信息, 只是把二义性从一个字段搬到另一个字段。

(不引用现有 spec 里那句"禁止版本标志"作为依据: 它只存在于本变更正在移除的那条 Requirement 中, 随本变更一并消失, 拿它论证等于援引一条即将不存在的规则。)

**替代方案 C —— 用持久化标记让迁移真正只跑一次** (`PRAGMA user_version` 或迁移表)。  **否决理由**: 升级那一次仍会造成一次丢消息, 而且如上所述, 那一次也是纯粹的伤害 —— 有益工作早已完成。  若改为"标记为已完成但不执行", 那就等价于删除, 只是多留了一段永不执行的死代码和一处需要维护的状态。

**选择删除的依据是时间线**: 迁移与 `register_agent` 的游标初始化由**同一个 commit** (`8f1c068`, 2026-05-08) 引入。  它的目标行只可能在该 commit 之前注册, 而任何**跑过含该迁移的构建**的数据库, 第一次启动就已把它们全部推进。  注意口径是"构建"而不是"启动": 迁移不持久化任何执行痕迹, 所以一个旧构建的 daemon 无论启动多少次都不会推进它们。  它的有益工作在所有跑过新构建的数据库上均已完成; 保留它等于只保留伤害。

### D2: 接受"陈旧库首次升级后会重放积压邮件"这一代价

一个从未跑过含该迁移之构建的数据库 (口径是构建不是启动), 其历史行游标停在 0, 该 agent 在升级后首次 `get_inbox` 会一次性读到积压邮件。

接受的理由是**两种失败代价不对等**:

- 保留迁移 → 静默丢消息, 收件人不知情, 发送端不被告警, **不可恢复**。
- 删除迁移 → 某个陈旧库的 agent 多读一批历史邮件。  它是**一次性**的, 且单次有上限 (`get_inbox` 取 `min(limit ?? 50, 200)`, 游标逐页推进), 属噪音, 可恢复。

这里要说清一个**不能拿来当论据**的东西: 30 天保留期并不在重放发生的那一刻封顶。  `runCleanup` 只由 daemon 的周期定时器调用 (默认一小时一次), 启动时不跑, 所以升级后的第一次 `get_inbox` 完全可能读到超过 30 天的邮件。  真正封住这件事的只有"一次性"和"单次页上限"两条。

在"静默丢数据"与"一次性噪音"之间, 选噪音。

### D3: 既有测试断言的是缺陷本身, 必须改写而不是保留

`tests/agents-cursor-watermark-migration.test.ts` 第一条用例 `advances zero cursor to MAX(event_id)` 断言的正是丢消息路径。  它之所以看起来合理, 是因为用例里用 `insertAgent` 直接写了一个游标为 0 的行 —— 那模拟的是"历史行", 但产品里同一形状也可能来自一次合法注册, 而测试无从区分。

同理, 那条 `is a no-op on the second run` 给了虚假的安心: 它之所以是 no-op, 只因为第一次运行已经把游标推离 0; 若游标**合法**停在 0 (空 events 表上注册), 第二次运行照样会推进。  这个案例既有用例从未覆盖。

改写方向: 删除断言"会推进"的用例, 换成断言 `applySchema` **不改动任何游标**, 并补一条按真实 `register_agent` → 发消息 → 重启链路复现原缺陷的回归用例 —— 用真实注册路径而不是测试助手, 因为缺陷的关键正是"真实注册在空 events 上也会产出 0"。

## Risks / Trade-offs

- **陈旧库重放历史邮件** → 见 D2。  一次性且单次分页有上限, 但**不受 30 天保留期约束** (清理只在周期定时器上跑, 不在启动时跑)。  明确接受。
- **已被吃掉的消息无法找回** → 本变更只止血。  受影响的消息行在 30 天保留期内仍在 `messages` 表里, 但无法判定哪些是被误标的, 因此不做数据修复。
- **`add-message-read-ack` 的 Known limitation 变成陈述历史** → 该段文字描述的缺陷在本变更后不再存在, 归档时需一并更新, 否则又变成一处"写下的话与事实不符"。
- **删除迁移后, 未来若再引入需要批量初始化游标的场景** → 需要重新设计一个无二义性的哨兵 (例如可空列或显式标志), 而不是复活这条按 `= 0` 匹配的 UPDATE。
